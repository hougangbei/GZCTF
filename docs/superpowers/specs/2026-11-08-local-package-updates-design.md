# 后台离线更新包：服务器目录与网页上传

状态：已确认两种入口及手动确认；实现前供用户审阅。

## 目标与边界

当前部署为业务机192.168.1.120上的离线Docker Compose平台，安装目录 `/root/nynuctf/runtime`，使用 `APP_IMAGE`、站点覆盖配置与既有题目SSH通道。用户希望以后通过后台完成更新，不必每次在终端解压和执行命令。

提供两个同等入口：扫描服务器指定文件夹中的包；在浏览器选择本机包并上传。两者进入同一验证、确认、备份、应用和恢复流程。发现或上传文件不自动更新。保留原GitHub/下载链接/源码目录能力，不改变原CTFd、比赛入口、Harbor或题目机。

不采用“仅增加文件选择框”的方案：现有ManagedUpdater识别的是源码或.NET发布目录，而本次GitHub下载包是Docker镜像离线包，两者清单和部署环境不同。新增offline部署适配器，复用 `deploy/offline/manage.py` 的安装身份、有效Compose配置、固定镜像指纹、备份、更新和恢复校验，不要求业务机安装.NET SDK、Node或pnpm。

## 后台流程

1. 顶部显示当前版本、镜像、更新服务连接状态和最近任务。
2. “服务器文件夹”填写业务机上的绝对路径，建议初始值 `/root/nynuctf/update-packages`；保存后手动扫描。扫描直接子文件，不递归，最多列出100个受支持归档。运维配置允许根目录，页面只能选择允许范围内的路径。
3. “上传更新包”支持选择或拖放 `.tar.gz`、`.tgz`、`.tar` 或 `.zip`，显示进度、大小、取消与失败重传。接收不等于安装。
4. 两种入口均支持附加官方SHA-256校验文件。目录扫描可发现同名校验文件；网页可同时选包与校验文件。没有校验文件时明确提示“未提供外部校验值”，仍校验内部清单；不将自算SHA-256表述为来源认证。校验文件存在却不匹配则阻止更新。
5. 点击“检查更新包”后，服务复制为不可变候选并计算摘要，识别版本、来源提交、架构和兼容性，检查内部文件清单、镜像身份、空间、当前安装及恢复状态。页面显示逐项结果。
6. 检查通过后显示旧版→新版摘要、备份位置和预期短暂停机，管理员勾选维护确认并点击“备份并更新”。不能根据文件名推断版本新旧，也不默认自动选中最近文件。
7. 更新页面持续显示校验、镜像导入、备份、停止应用、启动、健康检查、完成或恢复状态。服务由宿主机托管，应用自身重启和浏览器关闭不取消已确认任务。前端断连显示“正在重连”，恢复后读取真实任务状态。
8. 失败可恢复时使用匹配的数据库、文件、Redis和配置恢复原部署；恢复失败或任务中断显示需处理状态、备份标识和恢复指引，禁止继续应用。不得通过仅切旧镜像绕过数据库恢复。

整个页面跟随现有个人主题和深浅色。保留现有更新入口的兼容显示，离线部署默认展示离线包操作，不混淆“本机电脑”和“服务器目录”。

## 程序与权限边界

- 应用只做管理员鉴权、流式转发、状态与审计，不向应用容器新增Docker Socket、宿主机全盘或部署配置的写权限。
- 独立宿主机更新服务持有Docker/Compose能力，通过现有Unix Socket与私有令牌通信。新增offline部署模式，支持当前Compose项目、多个配置文件和APP_IMAGE变量。
- 上传内容流式写入服务专用暂存目录，以服务器生成ID命名；上传完毕后原子完成，取消或断流文件不能出现在可更新列表。初始上限1GiB，可由运维配置；控制请求JSON继续保持小上限，不能为上传放大所有接口。
- 对服务器路径先解析真实位置并按路径分量判断允许根；拒绝目录/文件符号链接、路径穿越、特殊文件、归档重复路径和解压炸弹。扫描数量、压缩大小、解压总量/数量都有边界。不得在待更新归档中加载Python脚本或使用包提供的任意命令；更新由固定宿主机工具执行。
- 支持当前发布包根目录的 `manifest.json`、`images.tar.gz`、Compose及更新所需文件；校验必要文件与镜像指纹，拒绝非linux/amd64及数据库/Redis不兼容包。只有当前已安装部署的更新，不提供网页首次安装。
- 同一部署仅允许一个写任务；共用离线更新器的文件锁，防止网页和命令行更新同时进行。检查报告绑定候选包摘要和当前安装身份，应用前重新核对，候选被替换或部署已变更时要求重检。
- 不自动清理备份、原包或失败候选。删除未使用上传包可另行扩展；第一版不提供备份删除或强制绕过恢复按钮。
- 审计记录上传、目录配置、验证和应用操作者、包摘要、结果和时间；网页不返回令牌、SMTP/仓库密码、数据库备份内容或原始命令输出。

## 接口轮廓

在现有 `/api/admin/updates` 下新增独立包操作，避免改变原source语义：

- GET/PUT `packages/settings`：服务器扫描目录、有效大小限制和部署能力。允许根和部署路径来自宿主机私有配置，页面不能扩大权限。
- GET `packages`：当前目录的有界扫描结果，返回候选ID、文件名、大小、修改时间和校验文件存在状态。
- POST `packages/upload`：受限流式上传；返回服务器分配的包ID及摘要。可单独提交校验文件，不信任客户端路径。
- POST `packages/{id}/validate`：创建后台检查任务。
- POST `packages/{id}/apply`：携带检查ID、当前部署版本、幂等操作ID和维护确认。拒绝过期检查、错误包ID及重复并发任务。
- GET状态继续由现有更新页轮询读取，增加上传/检查/更新任务的结构化字段，不改变旧客户端必需字段。

具体DTO与状态在执行计划中按已有客户端和服务实现统一；使用已有来源generation和校验过期机制的约束，不引入双套不一致的应用资格判断。

## 首次接入与发布

现有业务机是否已连接宿主机更新服务需要检测。若未接入，需要一次运维引导：安装固定服务代码、配置runtime路径和允许包目录、生成私有令牌、注册systemd、增加仅用于更新通信的挂载与设置，并校验连接。脚本必须保留原配置及题目通道，提供备份与重复执行保护，不接管其他容器。

应用新功能本身仍通过一个离线更新包首次部署；之后才可在后台上传或扫描更新包。不能承诺尚未安装的新页面能自行完成自身首次接入。新发行包应包含服务文件、一次接入脚本与更新说明；不自动更改远程正式环境。

入口Nginx需允许配置的包大小和上传时间；安装说明给出对应站点范围的设置与检查，不能全局关闭请求限制或改动比赛代理。

## 验证与验收

- 后端：管理员权限、大小/取消/断流、路径范围与符号链接、非法归档、错架构/清单/摘要、包替换、过期检查、重复点击和跨任务混用。
- 工具：真实Python3.8测试；目录与上传包汇合；命令行/网页共用锁；中断状态；失败恢复与禁止绕过。保留已有源码更新测试。
- 前端：两种入口、上传进度与错误、候选检查、确认时状态变化、断线重连、深浅色、键盘和移动端。
- 实际amd64镜像/隔离Compose：旧版接入服务→上传更新→后台重启后恢复任务→原账号/课程/排名/附件/配置保留；再从目录选包更新；失败候选恢复及幂等重试。不得对真实CTFd或真实业务数据做试验。

第一版验收结果：只需初次接入服务，以后管理员可以通过放包并扫描或网页上传完成同一套可验证、可恢复的更新。
