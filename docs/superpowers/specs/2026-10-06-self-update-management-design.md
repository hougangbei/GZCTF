# 平台更新管理设计

## 目标

管理员在后台查看当前运行的提交、GitHub 已成功发布的最新提交，并手动发起更新。更新只替换应用镜像；PostgreSQL、上传文件、配置和备份位于应用容器之外。源代码推送本身不作为可安装版本，只有镜像发布工作流成功的提交才可更新。

## 部署边界

- 目标部署方式为 Linux 上的 Docker Compose。新增示例部署文件，不改写现有部署。
- Web 应用不执行 shell 命令，也不通过更新功能访问 Docker Socket。管理员 API 通过仅挂载在应用和宿主机之间的 Unix Socket 访问宿主机更新程序。
- 更新程序的 GitHub 仓库、工作流、镜像仓库、Compose 文件、服务名称及备份目录由宿主机配置固定；HTTP 请求只能包含目标提交 SHA。
- 支持公开仓库；私有仓库可在宿主机配置只读 GitHub API 令牌，并提前配置 GHCR 拉取凭据。任何令牌不得返回前端或写入更新日志。

## 发布和版本检测

独立 GitHub Actions 工作流在 `main` 推送或手动触发时发布 `ghcr.io/<owner>/gzctf:sha-<40 位 SHA>` 和 `:main`。镜像标注完整提交 SHA。更新程序查询该工作流在 `main` 上最近一次成功运行，使用该运行的 `head_sha` 作为可用版本。状态接口返回当前容器镜像标注的 SHA、最新 SHA、工作流链接和更新任务状态；短时间缓存 GitHub 查询以控制调用量。最新 SHA 与当前 SHA 相同则禁用更新。

## 更新流程

1. 管理员确认目标 SHA，后台把它传给更新程序；更新程序重新核对该 SHA 仍属于最近一次成功构建，且一次只接受一个更新任务。
2. 在停止旧应用前拉取固定仓库中的 `sha-<SHA>` 镜像并检查镜像提交标注。
3. 停止应用容器，使用 `pg_dump` 生成数据库备份，并归档宿主机上的上传目录。备份失败则保持原镜像配置并重新启动旧应用。
4. 原子更新部署 `.env` 中的 `GZCTF_IMAGE`，只运行 `docker compose up -d --no-deps app`；数据库和 Redis 不重建。
5. 检查应用容器健康状态。成功后记录版本与备份路径。失败时停止不健康应用并保留备份；由于启动迁移可能已经改变数据库，不自动用旧镜像覆盖或降级数据库，由运维人员按照备份恢复。

## 安全和数据约束

- 后台更新 API 仅 `Admin` 可访问；执行操作写审计日志。Unix Socket 使用本地文件权限和独立共享密钥双重限制。
- 更新程序不接受任意镜像、仓库、Compose 参数、路径或 shell 命令。提交 SHA 必须为 40 位十六进制。
- 更新程序先返回任务已接受，再在后台执行；网页断线后可重新读取任务状态。
- 数据保留依赖真实部署时把 PostgreSQL 数据目录和 `/app/files` 挂载为持久化存储。自动迁移不可保证向后兼容，备份是更新前置条件。

## 页面

在管理员后台新增“更新管理”标签，显示当前/最新提交、检查时间、工作流链接、任务阶段、错误和备份位置。未配置更新程序时显示部署说明，不显示可用的更新按钮。更新前提供明确的确认弹窗，说明短暂停机、备份与数据库迁移风险。
